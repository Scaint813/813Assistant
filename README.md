# 813Assistant

Личный Telegram AI-штаб на aiogram 3.x + SQLite + APScheduler.

Пользователь пишет или говорит обычной фразой → бот понимает просмотр, создание или изменение → для записи показывает проверку → после подтверждения меняет данные.

---

## Что умеет

- **Доступ** закрыт allowlist-моделью: `ALLOWED_USER_ID` — владелец/admin, опциональный `ALLOWED_USER_IDS` поддерживает до пяти заранее разрешённых Telegram ID. Пустой список оставляет бота строго однопользовательским.
- **Свободный ввод без команд** понимает запросы на просмотр, создание, перенос, изменение, завершение и архивирование.
- **Голосовые сообщения** → OpenAI Whisper → тот же разговорный роутер и те же гарантии, что у текста.
- **Пакетный ввод**: несколько поручений отдельными строками превращаются в один понятный preview и одну атомарную историю действий.
- **Action Preview** показывает смысл, время и структуру до записи; его можно сохранить, изменить или отменить.
- **Профиль пользователя** — свой часовой пояс, рабочее окно, дневной лимит фокуса, размер рабочего блока, check-ins, тихий режим и стиль ответов.
- **Напоминания** через APScheduler — точное местное время пользователя (`18:20` и `18.20`), повторы, доставка с retry и рабочие кнопки (Выполнено / Перенести / Отменить).
- **Расписание ВШЭ** импортируется из `.ics` в структурированный календарь; опциональная приватная iCal-ссылка синхронизируется по расписанию.
- **Сводка и конфликты** объединяют пары, календарь, задачи, напоминания и сохранённое время в пути, не перепланируя задачи при простом просмотре.
- **Задачи** можно исправлять обычной фразой: «перенеси задачу про документы на завтра», «эта задача готова».
- **Проекты** — отдельные сущности `projects`, а не только текстовый ярлык: хранят цель, статус, ближайшее действие и связаны с задачами через `project_id`.
- **Недельный обзор** по фразе «подведи итоги недели» показывает завершённое, просроченное, препятствия и фактический следующий фокус.
- **Порядок задач** рассчитывается детерминированно и раскладывает конкретные дела в `now`, `next`, `blocked`; технические баллы пользователю не показываются.
- **Автоподсказки** выключены по умолчанию и при включении отправляются только по конкретным задачам с близким или прошедшим сроком.
- **Problem blocks** — активные блоки проблем, решение за 3 шага, snooze, архив, ресурсы.
- **Next step** — `/next` анализирует задачи / напоминания / блоки и даёт 1–3 действия.
- **Перегруз** — отдельный явно выбранный протокол в меню; обычный текст бот самовольно не перехватывает.
- **Miro sync** сохранён как опциональная ручная интеграция, но убран из основного UX на текущем этапе.
- **Журнал и undo** — `/activity` показывает реальные изменения, `/undo` отменяет последний пакет созданных сущностей.
- **Явная память** — `/remember`, `/memory`, `/forget`; бот не скрывает и не выдумывает сохранённые факты.
- **Apple Health / Calendar bridge** сохранён выключенным по умолчанию и пока не входит в основной UX.
- **Тренировки** — профиль, недельный план, напоминания и адаптация следующего плана по выполнению и RPE.
- **Cleanup** — `/cleanup` архивирует только мелкие просроченные задачи, не трогает важные.
- **Надёжность** — проверка DB/scheduler/jobs каждые 15 минут, уведомление владельца только при изменении состояния и ежедневный online-backup SQLite с ротацией.

## Telegram-интерфейс

Основной сценарий — обычный язык. Внизу остаются только две частые фразы, профиль и помощь:

- `Что у меня сегодня?`;
- `Покажи все дела`;
- `Профиль`;
- `Что ты умеешь?`.

Остальное вызывается так же, как формулируется человеком: «покажи напоминания», «разберём входящие», «открой настройки», «что делать сейчас», «покажи архив», «подведи итоги недели». Inline-кнопки появляются только после конкретного ответа и обозначают действие глаголом: `Завершить №1`, `Перенести №1`, `Разобрать входящие`.

Командное меню Telegram сокращено до стандартных `/start`, `/help`, `/settings`. Остальные старые команды не удалены из кода и работают для обратной совместимости, но пользователю их запоминать не требуется.

### Отложенные интеграции

Miro и импорт Apple Health/Calendar намеренно не участвуют в текущем основном сценарии: их кнопок нет в главном меню и в основных настройках, Health bridge по умолчанию выключен, а `MIRO_SYNC_ENABLED=false` полностью отключает фоновую синхронизацию Miro. Совместимый код и операторские команды сохранены, чтобы вернуться к интеграциям отдельным этапом после стабилизации разговорного UX.

### Закрытая многопользовательская готовность

По умолчанию вход не открыт: при пустом `ALLOWED_USER_IDS` middleware пропускает только `ALLOWED_USER_ID`. Для будущего подключения человека достаточно заранее узнать его Telegram user ID, добавить его в список и перезапустить сервис:

```dotenv
ALLOWED_USER_ID=111111111
ALLOWED_USER_IDS=111111111,222222222
MAX_ALLOWED_USERS=5
```

Повтор владельца в списке допустим и автоматически удаляется. Шестой пользователь или некорректный ID останавливает запуск с понятной ошибкой, а неизвестный Telegram-пользователь получает `Доступ закрыт.`

Задачи, reminders, problem blocks, previews, память, пользовательские экраны, quiet/check-in state, focus sessions, проекты, учебные и тренировочные данные хранятся и читаются по `user_id`. Check-in jobs создаются отдельно для каждого разрешённого пользователя. ReminderScheduler повторно проверяет allowlist перед доставкой, поэтому после удаления ID старое активное напоминание не продолжит приходить этому человеку.

Операционные debug-команды, текущая общая Miro-доска и Health/Calendar bridge остаются только у `ALLOWED_USER_ID`. Это намеренное ограничение: до появления персональных integration credentials данные нескольких пользователей не отправляются в общую внешнюю систему. `BOT_TOKEN`, OpenAI-ключ, модель и серверная таймзона пока общие для инстанса; содержимое запросов и метрики в БД разделяются по `user_id`.

## Первый запуск на сервере

```bash
# 1. Получить код
git clone <repo_url> /opt/bot/813Assistant
cd /opt/bot/813Assistant

# 2. Виртуальное окружение
python3 -m venv .venv
source .venv/bin/activate

# 3. Зависимости
pip install -r requirements.txt

# 4. Настройка
cp .env.example .env
nano .env          # заполнить BOT_TOKEN, ALLOWED_USER_ID и т.д.

# 5. Проверка кода
bash scripts_check_no_conflicts.sh
python -m compileall .

# 6. Первый запуск
python -m bot.main
```

При первом запуске `assistant.db` создаётся автоматически со всеми таблицами.

### Если assistant.db уже существует

Миграция применяется **автоматически** при каждом старте:
новые колонки добавляются через `ALTER TABLE` (idempotent — не ломается при повторе).

Если хочешь начать с чистой БД:

```bash
rm assistant.db
python -m bot.main
```

### Атомарное обновление

`deploy/deploy_remote.sh` создаёт отдельный каталог релиза с собственным virtualenv,
прогоняет compileall и тесты, делает online-backup рабочей SQLite, восстанавливает его
во временный файл и проверяет миграции на копии. Только после этого симлинк
`/opt/bot/813Assistant-current` переключается на новый релиз. Если процесс не остаётся
активным 15 секунд, `deploy/atomic_switch.sh` возвращает предыдущий релиз и перезапускает
service.

```bash
chmod +x deploy/deploy_remote.sh deploy/atomic_switch.sh
deploy/deploy_remote.sh 813assistant
```

Состояние (`.env`, `assistant.db`, backups) остаётся в `/opt/bot/813Assistant` и не
упаковывается в релиз. Пароли и токены в код или git не попадают.

## Backup SQLite

Основной production-backup встроен в бота и использует SQLite online backup API;
обычный `cp` живого файла не нужен. После создания копия автоматически проходит
тестовое восстановление, а отдельный job повторяет проверку последней копии ежедневно.
Скрипт ниже оставлен только как внешний запасной вариант для остановленного service.

```bash
# Настроить cron (бэкап каждый день в 03:00)
chmod +x deploy/backup_sqlite.sh.example
cp deploy/backup_sqlite.sh.example /opt/bot/backup_813assistant.sh

crontab -e
# Добавить строку:
0 3 * * * /opt/bot/backup_813assistant.sh >> /var/log/813assistant_backup.log 2>&1
```

Бэкапы хранятся в `/opt/bot/backups/813Assistant/`, ротация 14 дней.

## Голосовые сообщения

Pipeline:

```
voice → скачать файл → Whisper (OPENAI_API_KEY) → текст → intent parser → Action Preview → Confirm → DB
```

Если `OPENAI_API_KEY` не задан:

```
Транскрибация не настроена: отсутствует OPENAI_API_KEY.
```

Голос использует тот же parser, что и текст — отдельной бизнес-логики нет.

## OpenAI / Fallback parser

- Если `OPENAI_API_KEY` пустой → rule-based fallback parser, бот не падает.
- Рекомендуемый `Auto + Balanced`: простые intents → `gpt-5.6-luna` с low reasoning,
  планы и сложный анализ → `gpt-5.6-terra` с medium reasoning.
- `Economy` принудительно использует fast-модель; `Smart` — smart-модель; `Strict`
  сохраняет автоматический выбор, но уменьшает лимит ответа.
- `Economy / Balanced / Maximum` реально меняют объём контекста, reasoning effort и
  защитный лимит output tokens. Настройки читаются из `UserProfile` при каждом запросе.
- Детализация и тон влияют на формулировки и объём AI-планов.
- Если SMART не задан — fallback в FAST. Если оба не заданы — fallback parser.

## Action Preview

Бот **не сохраняет данные без подтверждения**.

Требуют подтверждения:
- `create_task`
- `create_reminder`
- `update_task` / `complete_task` / `archive_task`
- `update_reminder` / `cancel_reminder`
- `rest_day` / `schedule_override`
- `create_problem_block`
- `decompose_project`

Кнопки preview: **Сохранить**, **Изменить**, **Отмена**. «Изменить» принимает исправление обычной фразой, повторно прогоняет parser и показывает новый preview; исходный ошибочный вариант в БД не попадает. После сохранения появляется **Отменить последнее действие**. Undo восстанавливает не только создание, но и перенос/завершение задачи или напоминания.

Не требуют подтверждения запросы на чтение: «что сегодня», «покажи все дела», «покажи напоминания», «покажи проекты», «разберём входящие», «подведи итоги недели», «что ты умеешь».

### Разрешение ссылок на существующие дела

В контекст parser передаются ID и короткие названия только текущего пользователя. Сначала используется точный ID/название, затем безопасное нечёткое совпадение. Если одинаково подходят несколько сущностей, бот показывает до трёх вариантов и просит уточнить — ничего не меняет. После экрана дня/задач/напоминаний можно сказать «перенеси это» или «эта задача готова»: ссылка разрешается через `last_entity_type` + `last_entity_id`.

### Пакетный текст и голос

OpenAI parser может вернуть несколько intents с отдельным `source_text`. Fallback parser гарантированно разбирает список, если пункты разделены переводами строк. Нормализация времени и названия выполняется по своему пункту, поэтому время одного напоминания не попадает в соседнюю задачу.

## Напоминания

- Создаются через preview: "завтра вечером напомни проверить оплату Артёма"
- Сохраняются в `reminders` с `status=active`
- APScheduler планирует job `reminder:{id}` при confirm
- При старте бота все активные будущие напоминания перепланируются
- В момент срабатывания Telegram push с кнопками: **Готово / Перенести / Отмена**
- Snooze: +1ч / вечером / завтра утром / произвольное время фразой
- Повторы: `каждый день`, `по будням`, `каждый понедельник`, `каждый месяц`
- После успешной доставки повторяющееся напоминание переносится на следующий период; при ошибке доставки выполняются до трёх retry

Пример: `Напомни каждый понедельник в 18:20: тренировка` → preview показывает предмет `тренировка`, ближайшую дату, часовой пояс и повтор `weekly`.

### Профиль и местное время

Кнопка **Профиль** открывает один заменяемый экран, поэтому навигация по настройкам не засоряет чат. В нём доступны:

- часовой пояс: Москва, Алматы, Ереван, Никосия, Стамбул, Тбилиси или UTC;
- рабочее окно: начало и конец доступного дня;
- реальный дневной фокус: 2, 3, 4 или 6 часов;
- размер блока большой задачи: 45, 60, 90 или 120 минут;
- дни для задач: только понедельник–пятница или каждый день;
- check-ins одной кнопкой, тихий режим на два часа;
- стиль и детализация ответа, режим ИИ и расход контекста.

`UserProfile.timezone` применяется ко всему событию Telegram ещё до вызова обработчика. Поэтому одинаковая фраза «сегодня в 18:20» означает 18:20 Москвы для одного пользователя и 18:20 Алматы для другого; то же местное время получают прямые кнопки переноса, тренировки, экран дня и check-ins. У каждого reminder дополнительно хранится собственное поле `timezone`, чтобы SQLite-перезапуск не переосмыслил его как московское время.

После смены города новые данные сразу используют новый часовой пояс, а существующие напоминания не переписываются молча. Экран показывает число будущих напоминаний со старой зоной и предлагает отдельную кнопку **Исправить будущие напоминания**: при явном подтверждении сохраняются их дата и время на циферблате, меняется только выбранный город.

## Автоподсказки

Опционально не чаще одного раза в день через APScheduler (тот же instance, что reminders). По умолчанию `CHECKIN_ENABLED=false`: сначала пользователь осознанно включает функцию в настройках. Фоновые jobs уже зарегистрированы, поэтому кнопка начинает работать сразу, без рестарта.

Сообщение отправляется только по проверяемому триггеру: конкретная задача со сроком в ближайшие 24 часа/просрочкой; подтверждённая нагрузка на сегодня не помещается до 21:00 минимум на час; либо активный проект с реальным следующим шагом не менялся семь дней. Записи вроде «Задача», дела без срока и внутренний числовой рейтинг не являются поводом для сообщения. Одна сущность не повторяется в течение 72 часов. Обычные напоминания работают независимо.

Антиспам:
- `checkin_enabled=false` → не отправляется
- `quiet_until > now` → не отправляется
- Активность пользователя < 45 минут назад → не отправляется
- Уже была автоподсказка < 2 часов → не отправляется
- Та же сущность уже показывалась < 72 часов → не отправляется
- Максимум 1 автоподсказка в день

Quiet mode: кнопка [Тихий режим] → [На 2 часа / До завтра / Выключить автоподсказки].

Ручной тест:
1. Поставить `CHECKIN_DAY_TIME` на текущее время + 2 минуты
2. Запустить бота
3. Создать конкретную задачу со сроком в ближайшие 24 часа и дождаться автоподсказки

## Планирование без выдуманных приоритетов

Новая задача попадает прямо в план только когда известны её длительность и срок. Если данных нет, она сохраняется во **Входящие**, а `/inbox` предлагает короткие понятные варианты. Это не даёт модели молча превращать любое сообщение в «задачу на 30 минут со средним приоритетом».

`/calendar` вычитает реальные занятые события из окна 09:00–21:00, размещает только готовые задачи и отдельно показывает то, что сегодня не помещается. События календаря остаются read-only зеркалом: бот не меняет календарь и не считает его источником задач.

Фразы «дай мне любую задачу», «выбери одну задачу» и «какую задачу сделать» имеют отдельный read-only маршрут: бот выбирает одну **уже сохранённую** готовую задачу, объясняет причину выбора и предлагает конкретный рабочий блок. Такой запрос никогда не превращается в создание новой задачи или напоминания.

Фразы «помоги составить план на день», «что влезет сегодня» и «что взять, а что перенести» строят план внутри рабочего окна из профиля. Бот показывает учтённые календарные интервалы, задачи на сегодня, то, что не помещается, и запас времени. Если календарь не прислал события, это написано явно — скрыто считать день свободным бот не будет.

Оценка большой задачи не обрезается до четырёх часов. Например, задача на 40 часов сохраняется как 40 часов; на сегодня планируется только выбранный ограниченный блок, отдельно показываются остаток и ориентировочное число рабочих дней при личном дневном лимите. Это прогноз, а не обещание закрыть весь объём сегодня.

Кнопка **Разнести остаток по дням** сначала строит предложение на следующие 30 дней. Она вычитает календарную занятость и запланированные тренировки, пропускает `rest_day`, учитывает выбранные рабочие дни, не превышает дневной фокус и размер одного блока, показывает даты и интервалы, но ничего не сохраняет. Пользователь может выбрать **Подходит — сохранить**, **Изменить нагрузку** или **Не переносить**. Только после подтверждения будущие блоки записываются в `task_plan_blocks`; полная оценка родительской задачи не уменьшается. Повторное подтверждение пересобирает те же assistant-блоки без дублей.

В плане дня, списке напоминаний и preview напоминания часовой пояс показывается явно (`Europe/Moscow`, `UTC+03:00`). Это позволяет заметить неверную настройку до сохранения или ожидания доставки.

Read-only ответы, включая выбор задачи и план дня, обновляют один экран Telegram вместо накопления одинаковых сообщений в чате. Preview изменений и реальные push-напоминания остаются отдельными сообщениями, потому что требуют действия или должны сохраниться в истории.

`/focus` выбирает ближайшую готовую задачу. После сессии пользователь фиксирует фактический результат: завершено, ещё 15 минут или есть препятствие. При препятствии бот просит назвать его и не придумывает причину.

Фраза «покажи автоматизации» открывает активные/приостановленные напоминания и состояние контекстных подсказок. `/metrics` остаётся операторским экраном и показывает принятие и редактирование preview, количество уточнений, доставки reminder и реальные OpenAI tokens.

## Проекты и обзор недели

`projects` хранит цель, статус, срок и ближайшее действие. `tasks.project_id` связывает исполняемые шаги с проектом; старые задачи с одним `Task.project` безопасно привязываются при первом чтении. Запрос «разбей запуск магазина на конкретные шаги» создаёт/находит проект и связывает с ним весь пакет задач без дубля проекта.

«Покажи проекты» выводит реальный прогресс `готово / всего`, ближайшее действие, блокировки и срок. «Подведи итоги недели» считает только записи БД за последние семь дней и не выдумывает достижения или планы.

## Контур качества

Ассистент использует fail-safe разбор: непонятная фраза, вопрос о возможностях или критика ответа не превращаются в задачу. В таком случае бот просит уточнить действие. Для регулярной проверки хранится golden-набор из 40+ реальных русскоязычных формулировок: обычный текст, голосовые транскрипты, задачи, напоминания, переносы и неоднозначные сообщения.

Если в напоминании не хватает времени или предмета, бот задаёт один конкретный вопрос.
Ответ вроде «сегодня в 18:20» объединяется только с незавершённым запросом этого же
пользователя и только в течение 15 минут. Контекст другого пользователя не читается.
Время, длительность и дата сохраняются в структурированных полях и не засоряют название:
«купить витамины завтра на 15 минут» показывается как «Купить витамины» со сроком и
длительностью отдельно.

Preview использует подпись по действию (`Поставить напоминание`, `Добавить задачу`,
`Подтвердить изменение`). До сохранения доступны `Изменить` и `Это не поручение`.
После сохранения доступны `Всё верно`, `Исправить` и `Отменить сохранение`.
`Исправить` сначала атомарно откатывает созданный пакет, затем предлагает ввести
исправленную формулировку — поэтому исправление не создаёт скрытый дубль.

`quality_feedback` хранит оценку результата и SHA-256 исходной/исправленной формулировки;
сырой текст дополнительно не копируется. `/metrics` показывает долю исправлений,
завершение одношаговых уточнений, p95 разбора и p95 задержки reminder. Ежедневный
`system:quality_slo` уведомляет владельца только при новом нарушении измеримых целей:

- исправления среди оценённых результатов ≤ 20% (минимум 5 оценок);
- завершённые уточнения ≥ 80% (минимум 5 запросов);
- p95 разбора ≤ 8 секунд (минимум 5 измерений);
- неудачных доставок нет, p95 задержки reminder ≤ 60 секунд.

Все автоматические сообщения качества, backup и надёжности начинаются с пометки
**«Служебное уведомление 813Assistant»** и одинаково объясняют: что произошло, как это
влияет на работу и нужно ли что-либо делать. Пользовательские задачи и напоминания таким
форматом не оформляются; внутренние термины вроде SLO/p95 в уведомлении расшифровываются
обычным языком.

Каждое напоминание получает стабильный ключ события в `reminder_deliveries`. Повторный запуск одного и того же job не отправляет второй Telegram push; неудачная доставка сохраняется и повторяется не более трёх раз. Если процесс мог упасть уже после приёма сообщения Telegram, зависшая доставка помечается `uncertain` и не отправляется повторно вслепую — владелец получает сигнал для проверки. После перезапуска восстанавливаются только ещё не доставленные напоминания, просроченные не более чем на два часа, чтобы рестарт не создавал поток старых уведомлений.

Схема SQLite проверяется при старте. Применённые изменения записываются в `schema_migrations`; включены foreign keys, WAL, `busy_timeout`, а `PRAGMA integrity_check` должен вернуть `ok`. Ошибка обязательной миграции останавливает запуск вместо работы с частично обновлённой схемой.

Событие `intent_parsed` хранит путь parser/fallback, версии prompt и routing policy, источник и задержку без текста пользовательского сообщения. Операторский экран метрик показывает количество fallback, голосовых запросов, p95 задержки и неудачных доставок reminder.

GitHub Actions запускает конфликт-чек, компиляцию, Ruff и весь набор unit-тестов. Контрактный тест дополнительно гарантирует, что каждая показанная inline-кнопка имеет обработчик и не раскрывает внутренний callback ID пользователю.

## Контроль работоспособности и backup

При `RELIABILITY_ENABLED=true` APScheduler регистрирует системные job:

- `system:reliability` каждые 15 минут проверяет `SELECT 1`, состояние scheduler и наличие job у будущих активных reminders;
- `system:backup` ежедневно в 03:10 создаёт согласованную SQLite-копию через online backup API и сразу восстанавливает её во временную БД;
- `system:backup_verify` ежедневно в 03:25 повторно проверяет последнюю копию;
- `system:quality_slo` ежедневно в 08:45 проверяет метрики качества за семь дней.

Владелец получает Telegram-сообщение только при переходе в ошибку и при восстановлении, а не каждые 15 минут. Копии старше `BACKUP_RETENTION_DAYS` удаляются. Проверки не обращаются к OpenAI и не расходуют токены.

## /sync_miro — операционная доска

```
/sync_miro → создаёт/обновляет операционную доску в Miro
```

Miro — представление данных, а не база. Источник правды — SQLite.

Создаются только пять реальных Miro frames:

- `ПЛАН НА СЕГОДНЯ` — короткая сводка приоритетов, ближайших напоминаний, режима, рисков и шагов;
- `СДЕЛАТЬ СЕЙЧАС` — максимум три текущих задачи;
- `ПОСЛЕ ЭТОГО` — следующие задачи;
- `ПРЕПЯТСТВИЯ` — задачи с конкретным препятствием и активные нерешённые вопросы;
- `ЗАВЕРШЕНО` — счётчики и последние закрытые элементы.

Все новые рабочие элементы, включая Today/Done summary, создаются как Miro cards внутри frames. Карточка задачи показывает результат, конкретное следующее действие, длительность, timebox, дедлайн, проект, зависимости и препятствие — без внутреннего числового рейтинга. В TODAY есть недельный итог: сколько задач завершено за 7 дней и сколько проектов активно. Пустые секции остаются пустыми; декоративные sticky notes не создаются.

Дубли предотвращаются через `miro_mappings` (entity_type + entity_id + board_id).
При повторном `/sync_miro` существующие frames/cards обновляются. После подтверждения, закрытия или переноса сущности запускается фоновая debounce-синхронизация; ручная команда остаётся для контроля. Когда сущность закрыта, её активная bot-карточка удаляется и запись появляется в `DONE`. Старые декоративные bot-панели очищаются только по ID из `miro_mappings`; ручная зона пользователя не сканируется и не изменяется.

Левая граница каждого bot-frame не меньше `MIRO_AI_ZONE_START_X`.

Если `MIRO_ACCESS_TOKEN` или `MIRO_BOARD_ID` пустые:

```
Miro не настроен.
Нужно заполнить: MIRO_ACCESS_TOKEN, MIRO_BOARD_ID
```

## Apple Health bridge

Telegram Bot API сам не читает HealthKit. Реализован локальный HTTP bridge: Shortcut на iPhone с разрешения пользователя получает дневные агрегаты и отправляет JSON на `POST /api/health/snapshot` с Bearer token. Сохраняются только дата, шаги, цель, активная энергия, минуты тренировки и сна, пульс покоя и HRV — не медицинская карта и не отдельные HealthKit samples.

Если к `HEALTH_NUDGE_TIME` сегодняшняя запись свежая, дефицит не меньше `HEALTH_MIN_STEP_GAP`, тренировка не закрыла потребность и тихий режим не активен, бот один раз предлагает прогулку. Кнопки создают реальную задачу и reminder, откладывают решение на час или пропускают день. `/steps` показывает использованные значения.

Настройка iPhone Shortcut, payload, авторизация и reverse proxy описаны в [docs/HEALTH_SHORTCUT.md](docs/HEALTH_SHORTCUT.md). Пока bridge выключен или snapshot не пришёл, бот не придумывает показатели и не напоминает о шагах.

## Тренировочный план

1. Фраза «составь мне план тренировок» или `/training_setup` запускает пошаговый onboarding. Бот по одному спрашивает цель/приоритетные зоны, опыт, фиксированные занятия (`бокс вт 19:00 тяжёлая; футбол сб 12:00`), дни дополнительных тренировок, длительность, оборудование и ограничения. Каждый вопрос заменяет предыдущий экран, поэтому чат не засоряется.
2. `/training_plan` создаёт неделю и связанные напоминания; повторный вызов не плодит дубли. Экран остаётся компактным: вся неделя показывается по одной строке на занятие, а упражнения раскрываются только у выбранного дня. Кнопки дней и действий обновляют то же сообщение.
3. Фиксированные занятия сохраняются отдельно от составленных ассистентом. Для 2–3 дополнительных тренировок используются чередующиеся full-body акценты, для 4 — верх/низ, для 5–6 — push/pull/legs и балансирующие занятия. Если силовая стоит ближе 36 часов к тяжёлому фиксированному занятию, её объём автоматически облегчается.
4. Кнопка **Начать тренировку** включает пошаговый режим: бот показывает одно упражнение, плановые подходы, RPE и отдых. Фактические подходы записываются строкой `10x40, 10x40, 8x40` или `12, 12, 10` без веса. Упражнение можно пропустить; после последнего бот просит итоговый RPE. История сохраняется в `workout_set_logs`.
5. История подходов влияет на следующее совпадающее упражнение. Если верх диапазона повторений выполнен на двух тренировках при умеренном RPE, бот предлагает небольшой шаг веса; после высокого RPE или недобора нижней границы — немного снижает нагрузку; иначе сохраняет её. Решение и последний результат видны в карточке упражнения. После завершения занятия ещё не начатые тренировки текущей недели обновляются сразу.
6. На экране плана у выбранной тренировки есть кнопки **Начать**, **Перенести**, **Пропустить**, **Выполнено**. До переноса бот проверяет пересечение времени, совпадение с фиксированным занятием, интервал менее 18 часов между средними/тяжёлыми нагрузками и повторную нагрузку тех же мышечных групп ранее 36 часов. Затем можно выбрать **Перенести только эту** или **Пересобрать остаток недели**. Во втором режиме фиксированные и уже начатые занятия не двигаются, а напоминания гибких тренировок обновляются вместе с новым расписанием.
7. Перенос и пропуск понимаются обычным текстом: «перенеси тренировку на завтра в 19:00», «сегодня пропускаю тренировку». `/workout_done 7 нормальная тренировка` остаётся быстрым командным вариантом.
8. Следующая неделя слегка повышает общий объём при выполнении ≥80% и RPE ≤7, снижает при выполнении <60% или RPE ≥9, иначе сохраняет нагрузку.
9. Время занятия при необходимости сдвигается в ближайшее свободное календарное окно; при явном сигнале восстановления (сон <6 часов либо заметное отклонение пульса покоя/HRV от личной базы) объём снижается. Это не медицинский диагноз. При сообщении о травме, острой боли или сердечно-сосудистом риске автоплан блокируется до очной рекомендации специалиста.

## Apple Calendar через тот же Shortcut bridge

`POST /api/calendar/events` принимает read-only зеркало событий. Авторизация та же: `Authorization: Bearer <HEALTH_BRIDGE_TOKEN>`. Payload:

```json
{
  "source": "shortcut",
  "events": [
    {"id": "event-123", "title": "Врач", "start": "2026-08-03T17:00:00+03:00", "end": "2026-08-03T18:00:00+03:00", "is_busy": true}
  ]
}
```

iPhone Shortcut может получать события через `Find Calendar Events` на ближайшие 7–14 дней и отправлять массив в bridge. Повторная синхронизация заменяет зеркало в переданном диапазоне; создавать, переносить или удалять события бот через этот endpoint не может.

При словах о травме, острой боли, сердечно-сосудистом риске, обмороках или операции автоплан блокируется и просит очную рекомендацию специалиста. Это фитнес-планирование, не диагностика и не лечение.

### Диагностика Miro

`/miro_debug` проверяет доступ к доске. Логи сервиса:

```bash
journalctl -u 813assistant -n 120 --no-pager
```

`/miro_clear_bot_zone_preview` показывает, какие элементы из `miro_mappings` будут удалены. Ручные элементы пользователя в эту операцию не входят.
